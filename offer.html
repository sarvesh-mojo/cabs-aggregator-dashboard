This document explains how to create and configure offer codes in the database, and how the Offer Engine (controllers/offerController.js) evaluates and applies them at runtime.

Overview

The offer system supports:

  • Flat discount offers
  • Percentage discount offers (with optional max_discount cap)
  • New user, logged-in user, and guest user targeting
  • Device-specific offers (web, msite, app)
  • City-specific offers (with alias normalization)
  • Cab partner targeting
  • Time schedule based offers (SCHEDULE operator on current_time)
  • Budget-controlled offers
  • Total usage, per-user, and per-day limits
  • Stackable flag on offer payload (returned to clients; server applies one offer at a time)
Not handled by this controller: coupon code validation (offer_coupon_codes exists in the schema but is not read by offerController.js). Coupon flows are handled separately via getApplicableCoupons in fareSearchDTO.js.
Database Tables Used
TablePurpose

Scheduling and audience targeting are configured through offer_rules — not separate offer_schedule / offer_audience tables.

Non-applicable offers are still returned with "applicable": false. Offers with userVisibility = 0 are excluded unless caller === "applyOffer". Results are sorted: applicable offers first, then by highest discount.

applyOffer — request body
{ "offerId": "OFFER100", "searchId": "SEARCH123" }

On success, returns the selected offer plus fareDisplay and serializedFareDisplay. Re-applying the same offerId + searchId returns "Offer already applied" (idempotent).

removeOffer — request body
{ "offerId": "OFFER100", "searchId": "SEARCH123" }

Deletes all rows in offer_transactions for the given searchId (not a status update).

consumeOffer — request body
{
  "offerId": "OFFER100",
  "searchId": "SEARCH123",
  "bookingId": "BOOK456"
}

Sets booking_id and status = 'consumed' on the matching transaction.

Step 2: Add Offer Rules

Rules live in offer_rules. Each offer must pass all rule-type groups (AND across groups). Within a group, if multiple rules share the same rule_type, any one matching rule passes the group (OR).

Discount Calculation Logic

The engine uses two fare values:

  • Total fare (fare): used for min_cart_value check and finalPrice
  • Base fare (baseFare): used to compute discount when present and > 0; otherwise total fare is used
Flat offer
discount   = discount_value
discount   = min(discount, baseFare)   -- capped so discount never exceeds base
finalPrice = totalFare - discount

Example: fare = 1000, baseFare = 800, flat ₹100 → discount = 100, finalPrice = 900.

Percentage offer
discount   = (baseFare × discount_value) / 100
discount   = min(discount, max_discount)   -- if max_discount set
discount   = min(discount, baseFare)
finalPrice = totalFare - discount

Example: fare = 1000, baseFare = 800, 10% → discount = 80, finalPrice = 920.

Example with cap: baseFare = 800, 50% with max_discount = 120 → discount = 120, finalPrice = 880.

Runtime Validation Flow
getApplicableOffers
  1. Validate request body (Joi schema)
  2. If searchId present → validate fare cache; populate fare, baseFare, city, cabPartner
  3. Fetch active offers for client_id
  4. Fetch rules for those offers
  5. For each offer: skip if totalFare < min_cart_value; evaluate all rule-type groups; compute discount on base fare, finalPrice on total fare
  6. Sort: applicable first, then highest discount
  7. Filter by userVisibility (unless caller === "applyOffer")
applyOffer
  1. Validate offerId + searchId
  2. Validate fare cache via searchId
  3. Re-run getApplicableOffers (source of truth)
  4. Find offer where offer_id === offerId and applicable === true
  5. Build updated fareDisplay with discount line
  6. Idempotency: return success if already applied for same offer + search
  7. Begin DB transaction: lock offer_limits row (FOR UPDATE); re-check limits; insert offer_transactions with status applied; increment used_budget if budget configured
  8. Commit

Limits are not checked during listing — only on apply.

Offer Lifecycle

1. Offer Created 2. Rules Added 3. Limits Added 4. User Searches 5. Offers Listed 6. Offer Applied 7. Booking Done 8. Offer Consumed
  1. Offer created in offers
  2. Rules added in offer_rules
  3. Limits added in offer_limits (recommended for production)
  4. User searches ride → offers attached in fare search via getApplicableOffers
  5. User selects offer → applyOffer validates, checks limits, writes transaction
  6. User completes booking → consumeOffer marks transaction consumed
  7. User removes offer before booking → removeOffer deletes transaction

Transaction Management 
-- Check applied offers
SELECT * FROM offer_transactions WHERE status = 'applied';

-- Check consumed offers
SELECT * FROM offer_transactions WHERE status = 'consumed';

-- Remove applied offer (via API) — removeOffer deletes the row:
DELETE FROM offer_transactions WHERE search_id = :searchId;

-- Disable an offer
UPDATE offers SET status = 'inactive' WHERE offer_id = 'OFFER100';

-- Extend expiry
UPDATE offers SET end_time = '2026-12-31 23:59:59' WHERE offer_id = 'OFFER100';

Do not rely on setting status = 'failed' for removal — that is not what the API does.

Important Notes
JSON rule values

The value column should contain valid JSON when storing arrays or objects. Correct: '["DELHI","MUMBAI"]'. Also accepted: comma-separated strings like 'DEL,BOM' (auto-parsed to array).

userVisibility vs applicable
  • applicable: false — offer returned but rules/min fare failed
  • userVisibility: 0 — offer hidden from list API but still validated when applying by ID
Priority field

priority is stored on the offer record but runtime sorting uses applicable status + discount amount, not priority.

Fare search integration

During fare search (fareSearchDTO.js), offers are fetched automatically and attached to cab results. Manual API calls can also invoke /getApplicableOffers directly.

Troubleshooting
Offer not visible in list
  • status = 'active'
  • userVisibility = 1
  • start_time / end_time window (IST)
  • Rule evaluation failed → check applicable: false in full response (use caller: "applyOffer" to include hidden offers)
  • Device/city values match normalized form (app not android)
Offer not applicable on apply
  • Limits exceeded (budget, per-user, per-day, total usage)
  • Fare cache invalid or expired (searchId)
  • Rules no longer match current context
Discount looks wrong
  • Discount is calculated on baseFare, final price on total fare
  • Percentage offers respect max_discount
  • Discount is capped at base fare amount
"Offer already applied"

Idempotent response — same offerId + searchId already has an applied transaction. Call removeOffer to clear before re-testing.

Best Practices
  • Always add offer_limits for production offers
  • Set start_time and end_time
  • Use canonical device values (web, msite, app) in rules
  • Use city codes or known aliases consistently
  • Test with both list and apply flows
  • Monitor offer_transactions and used_budget
  • Use unique offer_id values per client
